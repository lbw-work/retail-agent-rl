# 阶段 02：Retail 环境与奖励验收

验证日期：2026-10-10。验证范围是本地环境与确定性评分，不是模型评测。
最终数量与通过状态以 `outputs/phase2_verification.json`、`outputs/phase2_tests.log` 为准。

已实际通过：参考操作成功 82/82；口头成功轨迹失败 82/82；错误目标轨迹失败 82/82；
每个任务的状态隔离、重置、评分不改变会话及提示一致性通过；26 项单元测试通过。

## 1. 这一阶段解决什么

阶段一准备的是“任务、参考答案和数据库快照”。阶段二把它们变成能实际执行的业务环境：

1. 客服调用查询、取消、换货等工具，得到真实业务返回。
2. 每次尝试从任务指定的数据库开始，修改只属于这次会话。
3. 一次交互结束后，评分器在另外两份环境里重放预测操作与参考操作，比较结果。

暂未加载 Qwen、调用 DeepSeek 或更新模型参数。本阶段付费计算费用为 0 元。

## 3. 代码与数据如何流动

```text
任务旁路字段：db_path、user_scenario、evaluation_criteria
     │               │                    │
     │               └─ 后续交给顾客       └─ 只交给评分器
     ▼
选择一份只读快照模板 → 深拷贝 → 当前 RetailSession
                                  │
客服可见：公开 policy + 工具 schema + 实际 user/assistant/tool 消息
                                  │
模型选工具和参数（阶段三实现） → call_tool → 官方 RetailTools → 实际返回
                                  │
                               完整轨迹
                                  ▼
                evaluate_task(task, trajectory)
                    │                      │
            新预测环境重放轨迹       新参考环境执行标准操作
                    └──── 数据库/声明条件判分 ────┘
```

程序不会用隐藏答案替客服选动作。验收脚本直接执行参考动作，目的是测试环境；
该脚本不能作为真实模型 rollout，也不能用于汇报模型成功率。

## 4. 实现文件的职责

| 文件/接口 | 作用 |
| --- | --- |
| `environment.py:_snapshot` | 解析任务快照并缓存初始模板；模板不交给执行工具 |
| `RetailEnvironment.make_tool_call` | 检查工具名、请求者、缺失/多余参数与严格参数类型，再交给官方业务函数 |
| `RetailEnvironment.get_response` | 将参数/业务错误变成工具反馈；内部程序错误继续抛出 |
| `create_environment` | 按经过路径检查的 `db_path` 选数据库；不使用默认官方数据库替代任务快照 |
| `RetailSession.reset` | 丢弃当前状态，重新深拷贝快照，并按任务配置重放初始状态与历史 |
| `RetailSession.call_tool` | 每次一个工具，保存匹配 ID 的客服调用和真实工具返回 |
| `RetailSession.agent_messages` | 生成与 SFT 相同的公开系统提示和工具协议；不拼接任务目标、参考动作或数据库路径 |
| `RetailSession.trajectory` | 返回消息副本，供评分与保存；外部修改副本不能改变会话 |
| `reward.py:evaluate_task` | 复用官方评估器、按 `reward_basis` 合并奖励，返回分项结果 |
| `scripts/verify_phase2.py` | 对固定任务执行成功/失败/隔离/重置检查，输出逐任务证据 |

业务函数、订单状态转换、退款金额和换货约束均来自上游，不在本项目重写。
完整 15 个工具的公开 schema 与阶段一保存的 schema 比对一致。
深度业务验收聚焦取消和换货，不能据此声称其余所有工具已充分测试。

## 5. 奖励实际在检查什么

现有 82 个任务均未显式覆盖默认 `reward_basis`，官方解析结果是：

```text
reward_basis = [DB, COMMUNICATE]
reward = DB_reward × COMMUNICATE_reward
```

`DB` 使用完整数据库内容的 hash 比较：参考环境和预测环境相同才为 1，否则为 0。
因此除了订单状态，还会比较取消原因、退款流水、礼品卡余额、换货商品与支付信息等字段。
额外错误写操作也可能造成数据库不同。

这不是逐行复制参考工具序列。查询次序不同、减少冗余查询，只要最终数据库相同仍可能得分。
测试特意验证“只执行正确写操作”能够通过 DB 判分，以说明这个边界。

`COMMUNICATE` 检查任务要求告知的信息是否出现在客服文本里；上游实现为不区分大小写、
去掉回复逗号后的子串匹配，不是语义事实核验。顾客说出这些信息不会代替客服满足要求。
现有 82 个任务的 `communicate_info` 全部为空，因此这一分项恒为 1，实际奖励信号来自 DB。
另用一个基于现有开发任务的测试夹具验证非空告知要求，未往训练集新增数据。

其它声明条件：

- `ACTION`：复用官方参考动作匹配，检测动作是否出现；它不是本批任务的奖励依据。
- `ENV_ASSERTION`：复用官方环境断言，按声明结果判分；用成功/失败夹具检查没有被忽略。
- `NL_ASSERTION`：暂未接入需要模型裁判的自然语言判定，遇到此奖励依据直接报错，
  不忽略该条件，也不自动调用付费模型。本批任务不依赖它。

**业务奖励不等于完整合规评估。** 工具描述要求身份验证、解释操作并取得明确确认，
但工具函数与 DB 判分并不会证明这些对话步骤已经发生。模型后续必须遵循公开 policy，
对身份核验、确认、越权承诺等另做规则审查；当前不引入未经验证的额外 RL 奖励。
只口头声称完成、没有改变数据库则不能通过这批任务。

## 6. 失败与异常如何区分

| 情况 | 当前处理 |
| --- | --- |
| 无效订单、订单状态不允许操作、缺失/多余/类型错误参数 | 工具返回 `error=True` 与错误文字，客服后续可修正 |
| 达到动作上限、连续错误上限或上下文上限 | 记为未完成轨迹，业务奖励 0，保留终止原因 |
| 网络或其它基础设施故障 | 抛出 `RewardEvaluationError`，不能作为普通零奖励训练数据 |
| 参考动作本身执行失败 | 抛出评分异常，不能让上游捕获异常后继续给一个误导分数 |
| 保存的工具返回被伪造、与重放结果不一致 | 官方重放检查报错，再转换为评分异常 |
| 未知奖励/终止配置 | 明确报错，不静默按成功处理 |

目前没有调用模型或网络，所以本阶段验证的是异常分流接口，并未验证真实限流、重试或计费。
一次工具错误不会自动让整条轨迹得 0 分；如果客服随后修正操作、完成业务且未触及终止上限，
仍按最终结果判分。工具错误次数和效率可以另作诊断指标。

## 7. 验收项目和证据

批量范围固定为 RL train 42、dev 10、test 30，共 82 个现成任务：取消 37、换货 45。
这些任务实际使用快照 1、2、4，分别为 45、12、25 个任务；快照 3 在本批选定任务中未被使用。
4 份快照文件均做了运行前后 hash 检查，不能把它当成快照 3 的完整业务执行验收。
这里读取最终测试任务的参考操作仅用于环境兼容验证，未按结果调整划分或训练参数。

每个任务执行以下检查，失败即中断，不删掉失败样本：

1. 执行全部参考动作，要求每个工具无错误，最终奖励为 1。
2. 只回复“成功完成”，要求最终奖励为 0。
3. 保留查询、将业务写操作的订单替换为不存在的订单，要求产生工具错误、最终奖励为 0。
4. A 会话执行参考操作时，B 会话数据库保持原样。
5. 对 A 的轨迹评分后，A 自身数据库不被评分器改动。
6. 重置 A 后，恢复初始数据库和历史；公开提示与数据文件中的 prompt 一致。
7. 全部运行前后，数据库及已固定的处理数据文件 hash 不变。

单元测试补充覆盖合法但错误的取消原因、重复取消/换货、不能取消已交付订单、
换货列表长度错误、计算器、工具参数、非空告知条件、环境断言、初始历史重放、
假工具返回、损坏的参考答案及内部异常。

机器证据：

- `outputs/phase2_verification.json`：每个任务的版本、奖励组成、正确/失败分数和状态检查。
- `outputs/phase2_validation.log`：批量运行记录。
- `outputs/phase2_tests.log`：单元测试通过/失败详情。
- `outputs/phase2_runtime.json`：Python/依赖版本、适配实现与测试源码 hash。
- `outputs/phase2_examples.json`：开发集取消/换货各一条参考工具轨迹，无模型或顾客参与。
- `outputs/phase1_recheck.log`：再次核验原始输入、处理数据、上游源码 hash 与划分隔离。

## 8. 如何复查和亲手调用

在项目目录运行；所有命令都是本地检查，不会下载模型权重或调用 API：

```bash
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v
.venv/bin/python scripts/verify_phase1.py
.venv/bin/python scripts/verify_phase2.py
```

阶段一的验证器只负责它自己的验收范围，输出里的“未验证环境奖励”是阶段一范围声明；
完整环境与奖励的当前证据应查看阶段二报告。如果重新执行 `audit_phase1.py` 重建数据，
需要再次执行阶段二验证，不应沿用旧报告。

重新建环境时，先按阶段一获取固定输入，再安装此阶段的依赖锁：

```bash
uv pip install --python .venv/bin/python -r requirements/environment.lock.txt
```

最小交互与评分示例，**这是工具接口演示，没有模型参与**：

```python
from pathlib import Path
from retail_agent.data import read_jsonl
from retail_agent.environment import RetailSession
from retail_agent.reward import evaluate_task

row = next(row for _, row in read_jsonl(Path("data/processed/rl_dev.jsonl")))
session = RetailSession(row)
print(session.agent_messages())       # 初始只有公开系统提示
print(len(session.tool_schemas))      # 15
session.add_assistant_message("Your request is completed successfully.")
result = evaluate_task(row, session.trajectory)
print(result.model_dump(mode="json")) # DB 不同，reward 为 0
session.reset()                       # 恢复初始状态
```

代码需要通过 `PYTHONPATH=src .venv/bin/python` 运行。真实业务参数应由后续客服模型根据
实际对话和查询结果产生；不要把参考动作循环写进 `rollout.py` 当作模型行动。
