## 本阶段的工作与验证范围

已实现本机模型推理、DeepSeek 顾客、单工具/文本解析、多轮控制、异常分类与持久费用记录。
本机有 16GB 内存，因此由固定原始权重派生 MLX 4-bit 副本，用于阶段三的接口与开发任务试跑。
没有换成其它 Qwen 版本或社区来源不明的模型；这次量化推理不是正式三组对照的共同运行环境。
后续训练、原始/SFT/SFT+RL 正式对照仍需固定统一的 GPU 推理条件。

原始权重约 8GB，三个 safetensors 分片的 SHA256 与 HF 固定 revision 的 LFS metadata 比对通过。
其它文件验证 git blob；原始文件与量化副本的 hash 记录在 `data/manifests/local_model.json`。
量化参数为 affine 4-bit、group size 64。比例中的 scale/bias 与少量未量化参数仍占空间，
不能把它理解为所有存储字节都恰好只有原始权重的四分之一。

依赖为本项目 Python 3.12 环境、MLX 0.29.2、mlx-lm 0.29.1、Transformers 4.57.6，
完整组合见 `requirements/phase3_local.lock.txt`。没有安装 PyTorch/TRL 训练栈。

独立真实模型探测：4,769 个输入 token、35 个生成 token，约 14.87 秒，MLX 记录峰值约 3.39GB。
这个探测只验证真实文本生成，不能据此声称完成业务；工具交互证据来自随后开发集试跑。

## 一条轨迹怎么推进

```text
仅顾客目标与已知信息 → DeepSeek 发起请求 → RetailSession 保存为 user
                                     ↓
公开规则 + 完整工具 schema + 实际历史 → Qwen3-4B 生成一个客服回合
                 ┌───────────────────┴───────────────────┐
                 ↓                                       ↓
        普通文本发给顾客                          一个 <tool_call>
                 ↓                                       ↓
      DeepSeek 根据目标和对话回复                官方 RetailTools 真实执行
                 ↓                                       ↓
         保存为 user，继续                       保存 tool 返回，客服继续
                 └───────────────────┬───────────────────┘
                                     ↓
                    顾客结束 / 限额 / 格式错误 / 服务故障
                                     ↓
                       保存原始事件、消息、终止原因与奖励
```

控制程序只做路由。它不会读取参考动作替客服决定工具、订单、商品或支付方法。
每个工具事件必须能对应上一条 Qwen 原始输出；离线验收会重放并核对这一点。

## 客服与顾客分别能看什么

| 角色 | 可见输入 | 不传入的旁路信息 |
| --- | --- | --- |
| Qwen 客服 | 公开 policy、15 个工具 schema、实际 user/assistant/tool 历史 | 完整顾客目标、参考操作、评分条件、数据库路径 |
| DeepSeek 顾客 | 当前任务的 `user_scenario`、公开口头对话、固定顾客行为规则 | 客服私有系统提示、客服工具调用及返回、数据库、评分答案 |
| 评分器 | 固定任务、完整预测轨迹、任务数据库、声明奖励依据 | 不向客服输出参考操作 |

顾客 API 的模型视角与业务角色相反：已有顾客发言是 API 的 `assistant`，
客服发言是 API 的 `user`。工具查询中不会调用顾客 API；客服说出一段话才让顾客回应。
顾客规则复用固定 tau2 源码的 `simulation_guidelines.md`，补充英文和私有工具不可见说明。
任务里已经给出的姓名、邮箱、订单等可由顾客逐步透露；不从评估答案补充这些事实。

## 非思考模式、原始 token 与训练边界

Qwen 使用固定 tokenizer 的 `enable_thinking=False`；DeepSeek REST 请求显式设置
`thinking: {type: disabled}`。若客服自行生成思考标签或顾客实际返回思考文本，会明确标记问题。

每个客服事件保留完整输入 token IDs、从流式生成直接取得的输出 IDs（含实际结束 token）、
原始输出文本、模型 log-softmax 分数、结束原因、耗时和峰值内存。
验收核对采样 IDs 解码等于保存文本，而不是事后重新编码文本冒充采样 IDs。

**这些轨迹不是可直接投入 GRPO 的训练批次。** 此阶段贪心温度为 0，记录的是模型
log-softmax，不是已验证的 GRPO 行为策略概率；下一回合仍重新按规范消息渲染上下文。
外部反馈训练掩码、完整序列追加一致性、组内对齐及一次参数更新留到阶段五验证。
结果中明确标记 `training_ready=False`。SFT 和 GRPO 入口仍未实现。

## API 费用如何控制

已通过本机 `.env` 完成接入；密钥不写入日志、轨迹、报告或来源清单。`.env` 被版本控制忽略。
客户模型保持 `deepseek-flash`，官方目前文档对应 DeepSeek-V4.1-Flash，显式关闭思考。
API 别名无法像本地权重一样永久固定，因此每次记录返回模型名与 `system_fingerprint`。

首次试跑上限 1 元，属于项目顾客 API 总预算 10 元的一部分；不租 GPU。
使用当前官方人民币高峰单价作保守上界：输入缓存未命中 2 元/百万 token、命中 0.04 元，
输出 8 元。[当前官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)

请求前按序列化消息的 UTF-8 字节与消息开销、最大输出预留上界；提示过大则停止。
每次尝试先落盘预留记录，返回后按实际用量与缓存命中计算高峰费用上界。
超时/断线等无法确定扣费的请求保留预留，重试另计；重启进程不会清空已累计额度。
首次试跑串行执行；账本暂不支持并发多进程抢占额度。

另外记录余额接口的前后差额。余额显示精度、更新延迟或同一账户的其它调用都会影响差额，
所以它不能代替逐请求账单；报告会区分“高峰费率上界记账”和“观察到的余额变化”。
当前费率有日期限制，阶段六及以后开始新实验必须重新核对，不把今天的价格当永久常量。

## 终止与失败分类

| 原因 | 处理 |
| --- | --- |
| 顾客返回 STOP/TRANSFER/OUT-OF-SCOPE 标记 | 结束本轮，按实际数据库和声明条件判分；顾客说结束不意味着成功 |
| 工具业务/参数错误 | 给客服真实错误反馈；连续三次错误结束 |
| 客服输出混合文本/多工具/思考标签/非法结构 | `invalid_model_output`，未完成任务的零奖励 |
| 客服生成长度或上下文超限 | `generation_limit` / `context_limit`，保留记录，零奖励 |
| 达到动作数上限 | `max_steps`，按未完成处理，不伪装成功 |
| 顾客 API 被截断、为空、网络/权限/服务错误 | `customer_service_error`，奖励为 null，不作为客服业务失败 |
| 费用不足以预留下一次请求 | `budget_limit`，停止，奖励为 null |
| 模型/执行或评分内部故障 | `infrastructure_error` / `grading_error`，奖励为 null |

## 已发现的真实问题

取消开发任务 `retail_107` 中，模型完成了真实取消，但自行选择 `no longer needed`，
参考答案为 `ordered by mistake`，完整 DB 比较因此为 0。模型没有先让顾客选择原因，
也没有在实际取消前取得明确确认；这些是后续 SFT 和规则审查需要改进的行为。

同时，该任务的顾客目标要求选择合法取消原因，却没有固定参考答案中的具体原因。
若客服正确询问、顾客自然选择另一合法原因，仍可能与完整 DB 参考结果不同。
阶段三保留原始任务和评分，没有改奖励让案例显得成功。进入 RL 前应核查取消任务中
用户目标与严格评分条件的一致性；不能通过把参考动作塞入客服提示来绕过这个问题。

换货试跑也出现将工具说明中的示例 item ID 当作真实 ID 的行为，工具正确返回错误。
完整案例与最终结果由实际轨迹说明，不能把工具调用格式正确等同于业务能力通过。
