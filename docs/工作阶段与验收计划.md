## 项目目标与完成定义

训练一个使用 `Qwen/Qwen3-4B` 的电商售后客服 Agent：先学习现成 SFT 示例，
再在现成 RL 任务上与 DeepSeek 模拟顾客交互，由业务结果产生奖励，使用成熟框架更新 LoRA。
最终提供人工对话演示、可加载模型适配器和可追溯对照评估。

第一版使用完整 Retail 售后范围：取消、退货、换货、修改订单地址、商品、付款方式、用户默认地址；
RL 保留通过验收的单一及复合任务，按不同写操作类别数量分 single/pair/complex。
旧阶段一的 42/10/30 个 RL 任务与阶段三试跑属于 v1 历史记录。
当前数据文件、实际数量与离线验收见 [数据集 v2 报告](数据集v2_重建与验收报告.md)。
界面中文、训练与评估对话英文；中文业务能力不列为第一版验收项。

最终完成必须具备：

1. 数据来源、环境和模型版本、划分清单可追溯。
2. 正确加载任务数据库，轨迹之间状态隔离，隐藏目标与评估答案不泄漏。
3. 真实 SFT 与真实多轮 GRPO 的参数更新证据，并保存可加载适配器。
4. 三组模型在相同条件下的结果、完整轨迹和失败分类。
5. 人工顾客可使用同一模型与工具执行路径交互，查看工具和业务状态变化。
6. 实际总费用不超过 50 元；不能保证训练后一定提升。

## 阶段 01：数据与版本核查

**前置**：阶段 00。

**工作**：

1. 获取现成 AReaL SFT/RL JSONL 与 Retail 数据库，固定数据集 revision 与文件校验值。
2. 逐行解析 JSONL，不假定数据查看器/自动 Arrow 推断可以处理异构工具参数。
3. 识别 Retail 样本，统计对话数、目标回合数、业务类别和任务数量。
4. RL 的 `evaluation_criteria` 若为 JSON 字符串，先解析并检查结构；解析 `db_path`。
5. 用实际 Qwen tokenizer 统计上下文及目标回合长度，检查工具名称、参数与格式。
6. 核查数据使用的业务规则与环境版本。tau2-bench 最新 main 已有变动，不能直接假定兼容。
7. 用任务操作和顾客诉求识别业务类别，区分纯取消、纯换货、混合诉求；检查任务是否可解。
8. 按对话、场景及来源模板分组，再划分 SFT/RL 训练、开发与最终测试；检查近似重复。
9. 全量审查 11,395 个 Retail SFT 回合和 563 个 RL 任务，保留适用样本，不再设置 1,500 条的筛选上限。
10. SFT/RL 联合划分约 70%/15%/15%，实体、场景和词面模板整组分配；保留旧 dev/test 侧，冲突组隔离。
11. SFT 使用完整上下文，按 ≤8,192、8,193～12,288、12,289～16,384 token 分桶；最终测试侧示范封存。

**当前规模规则（最终数量以 v2 报告为准）**：

| 数据 | 起步目标 | 选择逻辑 |
| --- | --- | --- |
| SFT 候选池 | 所有通过检查的现成回合 | 不限制为 1,500 条；预算决定实际训练量 |
| SFT 开发 / 封存 | 同一联合划分的 dev / test 侧 | test 示范不参与训练、调试或选检查点 |
| RL 训练 | 全业务、各难度通过验收的 train 侧 | 之后按类别和难度采样，预算试跑后确定次数 |
| RL 开发 | 联合划分的 dev 侧 | 用于调试和选检查点，不用作最终结果 |
| 最终测试 | 联合划分的 test 侧 | 固定清单，不能通过测试表现调整训练数据 |

SFT 与 RL 数据未必有统一 ID；需要检查描述、场景、数据库实体和来源模板，
不能只凭 ID 不同证明独立。如果无法证明严格无泄漏，明确记录限制。
只筛选高质量示范，不把现成 `correct=1` 当成无需检查的质量保证。

**产物**：

- `data/versions/retail_full_v2/manifests/`：固定来源、SHA256、分组、逐行排除原因、工具 schema。
- `data/versions/retail_full_v2/reports/`：全量参考检查、数据统计、独立验收、重建一致性记录。
- `data/versions/retail_full_v2/processed/`：SFT 与 RL 的 train/dev/test 六个文件。
- `data/provenance/`：固定原始来源与 68 条旧留出节点；完整旧样本和重复归档已清理。
- `docs/history/`、`outputs/reports/history/`：必要历史记录；真实轨迹和费用账本仍保留。

**验收**：划分可重建、隐藏字段不进入客服提示、每条 RL 任务能解析并定位数据库；
全部原始任务的纳入/隔离有记录，业务覆盖及样本数量有报告依据。
RL 参考/口头宣称/错误目标、状态隔离/重置/评分不修改状态的离线执行证据可追溯；不等同于模型测试。

## 阶段 02：Retail 环境与奖励验证

**前置**：阶段 01。

**工作**：

1. 在 `third_party/tau2-bench` 放兼容版本源码，固定 commit，不重新实现订单业务逻辑。
2. 加载业务规则与完整工具定义，按任务快照创建环境。
3. 每条轨迹使用独立状态；参考操作在另一份初始环境执行，不能修改预测环境。
4. 先用任务参考操作验证金标准结果，再构造失败操作验证评估器能区分。
5. 核查所用版本的奖励组成：数据库、告知信息、其他任务声明的条件。
6. 接入 `environment.py` 与 `reward.py`，返回真实结果及可检查的评估细节。
7. 对无效订单、工具参数错误、重复操作、环境重置编写有意义的小测试。

**关键例子**：同一取消任务开始两条轨迹；A 成功取消后，B 的初始订单仍应是未取消。
如果 B 已看到 A 的修改，环境隔离失败，不能进入训练。

**产物**：环境/奖励实现、`tests/test_environment.py`、`tests/test_reward.py`、环境版本与验证报告。

**验收**：正确参考操作得到预期结果；只口头宣称成功不能通过；
任务之间和组内轨迹不串状态；评估条件不暴露给客服。

## 阶段 03：真实模型与多轮交互接入

**前置**：阶段 02。

**工作**：

1. 固定 `Qwen/Qwen3-4B` revision，加载模型/tokenizer，关闭思考模式。
2. 使用相同的业务规则、工具 schema 与消息序列化，解析模型生成的工具调用。
3. 实现 DeepSeek 顾客：只读取自己的目标/已知信息和必要对话，不读取客服隐藏评估答案。
4. 密钥通过本地环境变量读取；记录实际模型名、参数、输入/输出 token、错误与费用。
5. 区分客服消息与工具调用：前者交给顾客，后者交给工具，返回后继续生成。
6. 规定任务结束、顾客结束、最大动作数、上下文长度和服务异常等终止原因。
7. 工具错误作为可见反馈；网络与限流故障单独标记，不当作业务失败。
8. 保存原始模型少量开发任务轨迹，检查工具格式、循环、业务成功与资源开销。

**产物**：`customer.py`、`rollout.py` 的交互部分，`outputs/pilot/original_traces.jsonl`。

**验收**：客服询问信息后能继续对话；至少完成一条真实工具执行链；
模型、顾客、工具三者来源能区分；异常有明确记录；不由程序读取答案代模型选择业务动作。

**决策点**：基础能力不够时先判断是协议问题还是模型问题。
任何模型更换都需明确与用户讨论，不能静默用其他模型替代。

## 阶段 04：SFT 冷启动

**当前状态**：正式 Qwen3-4B SFT 已完成，适配器本机加载及 14 条开发任务对照已验证；训练详情和限制见 README 与开发集评测报告。

**前置**：阶段 01～03。

**工作**：

1. 固定通过验证的 PyTorch/Transformers/TRL/PEFT 版本组合，生成依赖锁定记录。
2. 转换为“上下文 + 当前目标客服回合”，工具名与参数格式和推理端一致。
3. 非思考模式不监督独立 thinking 字段；清理提示中的强制思考要求，保留业务政策。
4. 目标之前的 system/user/tool/历史 assistant 标签设为忽略，目标客服 token 与结束符参与损失。
5. 检查 token 前缀边界，不能假定模板自带 assistant mask 或直接靠字符串长度定位标签。
6. 根据真实长度选择上限，过长样本明确排除或采用经过核查的处理方法，不静默截断答案。
   当前数据上限为 16,384 token；先测各长度桶显存、吞吐和费用，再决定训练量，封存 SFT test 不参与训练。
7. 先做最小前向/反向更新，再开展小规模一轮 LoRA SFT；费用全程累计。
8. 保存 SFT 适配器，并重新加载运行开发任务；用开发集判断是否已有业务成功机会。

**产物**：`train_sft.py`、数据 collator、掩码检查、`outputs/sft/`、损失日志、开发轨迹。

**验收**：LoRA 参数实际变化；基础权重按设计冻结；目标边界正确；
适配器可重载；能生成合法工具调用并在代表性开发任务上完成部分业务。

SFT loss 下降不等于业务能力通过。若任务仍全部失败，不直接扩大 GRPO。

**工作**：

2. 对照顾客目标、顾客可提供的信息、商品库存、订单和参考操作。保留原始来源与排除理由，不重划分，不改隐藏金标准制造成功。

6. 以真实环境重放构造可达的原子业务子集，在轨迹结束时验证完整数据库及实际成功执行；包含退款和余额副作用。不奖励查询次数、口头宣称或每次工具调用，不拆分只能一次提交的原子商品修改。任务 196 的付款依赖取消退款，不可达子集明确排除。

**产物**：训练任务清单与来源哈希、语义复核记录、奖励版本说明、各分项结果及奖励反例测试。

### 05B：采样与训练接口准备

**已完成（离线）**：固定 TRL 0.26.2 的非 vLLM 采样适配，保留原生优势与损失；追加实际客服 token，外部反馈掩码直接在损失梯度中验证。24 项专项通过，两环境合并覆盖全部 97 项。固定底座、SFT 成果、任务池哈希与训练依赖已核对；只读入口为 `train_grpo --preflight`，正式 GPU 启动待 05D。详见 [05B 报告](阶段05B_多轮GRPO接口与异常验收.md)。

**工作**：

1. 核查固定 TRL 0.26.2 的自定义 rollout 接口、分组和概率信息要求，复用框架更新逻辑。
2. 将训练随机采样与固定评测分开；每任务先用 4 条尝试，初始状态相同、状态对象独立，顾客设定固定。采样温度是待验证配置，不直接改已有评测条件。
3. 核对真实 SFT 适配器路径，训练从 SFT 副本继续更新 LoRA，原 SFT 产物保留作对照，底座按设计冻结。
4. 记录真实采样 token、旧策略概率、回合边界和可训练 token 掩码；追加工具/顾客信息不改写已有 token 序列。拒绝用解码再编码的近似序列代替原采样 token。
5. 只对客服生成文字和工具调用计算策略损失；顾客、工具返回和提示只作上下文。先在完整任务组内计算优势，再按显存拆微批。
6. 先做局部的分组、掩码、前缀和异常分类验收。测试数据只能证明接口逻辑，不当作真实模型采样或参数更新证据。

**产物**：采样配置、TRL rollout 适配、分组和掩码检查、训练入口及正确的 SFT 加载路径。

**验收**：隐藏目标不进入客服输入；非客服 token 不参与策略损失且保留注意力；任务组不串状态；真实小模型采样概率与更新概率一致。4B/CUDA 仍须 05D 实测。现有 MLX 评测轨迹不能直接当作 CUDA 训练策略的 on-policy 样本。

### 05C：SFT 组内采样诊断

**2026-10-13 当前状态**：真实采样、恢复及国家等价奖励验收完成；多个任务有真实业务差异。首批历史 30 条中 retail_494 因顾客邮箱指向其他用户而隔离，目前配置使用 29 条可用池，原始数据和历史记录保留。经用户确认，训练奖励仅统一 USA/US/United States，其他字段及检查严格保留。现有 32 条轨迹官方成功数仍为 13，新训练奖励认可 14 条成功，这是纠正误判而非训练提升；详见 [05C 报告](阶段05C_SFT组内采样诊断.md) 与 [05D 启动前检查](阶段05D_GRPO启动前检查.md)。

**前置**：05A/05B、费用账本核对及本阶段 API 授权。

**工作**：选约 8～12 条已核对的 TRAIN 任务，每任务采样 4 条，共约 32～48 条真实轨迹，先不更新参数。可在本机做初步诊断；MLX 的结果仅表示本机策略表现，训练后端仍须在 05D 重新验证。

**记录**：完整业务全零组/全一组/混合组、部分分差异、终止原因、工具与协议错误、政策指标、轨迹长度、API 用量和耗时。即使训练过滤同分组，诊断报告仍保留全部采样记录。

**验收与分支**：

- 在多个任务上出现由真实业务完成情况产生的组内差异，且部分任务已有完整成功机会，才支持进入小规模业务优化试验；不能只靠格式分或评分噪声制造有效组。
- 大量全失败：先定位任务语义、协议、环境或基础能力。只有确属基础能力不足时才提出针对性的 SFT 补训，数据仅来自 TRAIN 侧现成示范，额外费用另行把关。
- 大量全成功：选择仍然可信但更有挑战的 TRAIN 任务，不立即增加组大小。
- 差异主要来自 API 故障或奖励错误：先修复，不进入训练。

**产物**：完整诊断轨迹、按任务和业务类别的统计、继续/回退建议及费用实测。部分奖励差异增加不等于训练后会提升。

### 05D：训练后端的一次真实参数更新

**前置**：05C 有可用学习信号、费用预留足够、GPU 操作已获阶段授权。

以下检查必须使用训练后端的新轨迹，不能用之前的 MLX 评测轨迹替代。

**工作**：

1. 核查所固定 TRL 的自定义 rollout 接口、批次分组与概率信息要求。
2. 将同一任务复制为组内 4 条尝试，初始状态相同，状态对象独立。
3. 保留实际采样 token 和旧策略所需信息；外部反馈可进入注意力上下文，但不能作为客服目标。
4. 验证追加消息不会改写过去的序列；拒绝把解码后重新编码的近似序列当原采样序列。
5. 根据固定版本正确提供 `env_mask` 或等效训练掩码，检查其在损失中实际生效。
6. 将整条轨迹的任务奖励接入 GRPO，框架负责优势、裁剪及优化器更新。
7. 先用受控交互检查掩码，再完成一组真实交互和一次真实参数更新。
8. 记录成功/失败分布、组内奖励差异比例、有限损失、梯度及参数变化。

**产物**：`train_grpo.py`、TRL 适配代码、掩码/组对齐测试、一次更新证据与小检查点。

**验收**：顾客与工具 token 不参与生成损失；任务分组正确；损失和梯度有限；
适配器参数确实变化且可重载；没有把网络故障伪装为零奖励业务样本。

这一步是技术接入验证，不宣称训练提升。全零奖励导致无有效优势时，
应补充有成功机会的 TRAIN 任务或根据诊断改善 SFT，不能将 DEV 转为训练任务，也不能制造虚假奖励通过验收。

## 阶段 06：费用试跑与规模确定

**前置**：阶段 03～05；之前费用已经累计。

**预算**：总上限 50 元不变。初始分配为 GPU 35 元、API 10 元、其他/预留 5 元，不能静默越过任何已配置上限。

2026-10-12 本地账本的顾客 API 累计记账上界为 0.26606336 元；用户确认已发生服务器费用不超过 35 元，精确实际账单仍需核对。按 35 元服务器费用保守计算，剩余约 14.73 元，保留 5 元收尾额度后，新试验可用约 9.73 元。此计算不是 GPU 或 API 的新报价，也不是未记录费用为零的保证。

若服务器实际已接近原 GPU 35 元上限，下一次租卡前须由用户把关是否从未使用的 API 配额重新分配，随后再更新预算配置。未批准重分配时不得直接开启超 GPU 配额的训练。

**工作**：

1. 记录租卡实际价格、存储计费方式、API 当前费率与结算币种，不用历史价格代替实际价格。
2. 汇总已有消耗，测量少量完整轨迹以及“采样 + 更新”的总耗时、显存与 token 用量。
3. API 输入包含顾客提示与反复发送的历史，GPU 等待 API 的计费时间也包含在估算中。
4. 先预留三个模型的最终测试、保存、下载和关机费用，再确定允许的新训练量。
5. 比较实际完整序列长度与显存，按实测选择微批/累积方式。
6. 在 45 元停止启动新工作，并保守估计在途请求费用；不能等账单达到 50 才停止。
7. 建立每批次启动前费用检查；GPU 关机/停止计费仍需平台侧确认，程序退出不等于停止租卡。

**规模计算例子**：若每更新采样一个任务的 4 条轨迹，20 次更新对应 80 条训练轨迹。
三个模型各评估 30 个任务、一次尝试，共 90 条评估轨迹。开发试跑与重试另计。
如果一个更新消费更多任务组，应按实际组数重新计算，不能沿用这个例子。

**产物**：`outputs/budget/pilot.csv`、`cost_plan.md`、更新后的配置及实际费用账本。

**验收**：估算有实测数据，费用累计包含前期试跑，最终评估有预留；
规模不能落在预算内时，先缩小未开始的训练量，不承诺补做付费实验。

## 阶段 07：小规模真实 GRPO

**前置**：阶段 05/06。

**工作**：

1. 从 SFT 检查点继续训练，单卡、同步采样与更新；先执行 5 次更新级别试跑。
2. 跟踪业务奖励、组内差异、无效工具调用、轨迹长度、耗时和费用。
3. 根据开发集和剩余预算决定是否继续，不用最终测试结果决定继续训练。
4. 定期保存适配器与可恢复状态；记录检查点与训练步数对应关系。
5. 连续全失败时先检查任务、环境、规则、掩码和 SFT，不无限重复无信号采样。
6. 部署推理检查点与训练参数要同步，避免继续采样旧策略而未记录。
7. 第一轮只使用 05A 验收后的训练池与选定奖励版本；以 5 次更新试跑为起点，训练轨迹量按“更新数 × 每更新任务组数 × 组大小”实算，不承诺固定训练轮数或覆盖整个 364 条池。
8. 训练奖励 A/B 的优劣须用相同 SFT 起点、数据和近似采样预算比较。费用不足以运行两组训练时，只选一个目标开展探索，离线奖励比较不能被写成训练消融实验。
9. `group` 与 `batch` 奖励缩放可作为后续单变量实验；只有批次含多个任务组时才有实质区别。不同时改奖励、缩放、学习率和任务难度后归因于一个因素。
10. 根据固定开发评测决定是否继续；完整成功率或可靠政策指标退化时停止扩训并保留原 SFT，不靠训练平均分上涨证明收益。

**产物**：`outputs/grpo/`、训练轨迹、指标、检查点、配置快照与费用记录。

**验收**：有真实多轮交互和真实参数更新；训练记录可追溯；最终模型可加载；
费用不超上限。性能提升留给阶段 08 检验，不能用训练奖励代替留出集效果。

## 阶段 08：三组对照评估

**前置**：阶段 07；保存原始模型和 SFT 的可加载状态。

**工作**：

1. 先完成固定 DEV 对照并选择检查点，再冻结模型、奖励版本、协议、评测清单与预算，最后评估原始、SFT、SFT+GRPO 三组封存 TEST。现有 14 条 dev 对照继续保留；全部 75 条 dev 的扩展评测以实测费用和资源为条件。
2. 相同顾客模型/提示/参数、工具规则、数据库、轮数和 token 上限；记录随机设置。
3. 区分业务失败、截断、系统故障，报告预定任务数与实际完成数，不能悄悄删除失败样本。
4. 主指标为成功数/总任务数，同时报告百分比；30 个任务中 1 个任务约改变 3.3 个百分点。
5. 报告合法参数、成功任务平均轮数/工具次数、失败类别以及固定样本的人工规则审查。
6. 记录原本成功后变失败的任务，观察退化；其他业务补充评估仅在费用允许时执行。
7. 不与顾客模型和环境版本不同的官方榜单直接比较，不声称完整 Retail 能力已验证。
8. 训练采用部分奖励时，主评测仍单独报告原有完整业务成功率，并另列子目标完成率、已验证政策指标、系统故障和费用。不同奖励版本的训练平均分不能直接横向当作性能。
9. 最终 TEST 当前有 75 条任务，优先规划三组共 225 条轨迹的一次固定评测；费用不足需在打开 test 结果前按既定分层方法冻结较小清单并明确覆盖限制，不按结果挑任务。最终评测后不据其结果调训练和选检查点。
10. DEV 已知语义疑点另作说明，原有分数不事后删样本美化。TEST 若发现疑点也保留原成绩和问题说明，不用该样本反向训练。

**产物**：`outputs/evaluation/summary.csv`、三组轨迹、`report.md`、失败案例与简单图表。

**验收**：表格每个数字能对应任务和轨迹；有一致实验条件；
如无提升或结果不稳定，报告真实结论、样本规模与可能原因，不筛选好看案例代替整体结果。
