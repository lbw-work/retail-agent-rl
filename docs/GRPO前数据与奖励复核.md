## 结论和使用边界

阶段 05 的**一次真实参数更新验证**可从 `reviewed/rl_train_smoke.jsonl` 的 8 条任务开始；七种写操作和一条复合任务均有覆盖。原始 364 条训练任务不宜直接整批用于正式 GRPO。自动筛查得到 241 条未触发已知疑点的候选任务、8 条逐条核对的起步任务、115 条待复核任务。241 条仅表示通过本轮规则，不等于逐条人工证明语义无误；阶段 07 扩大训练前，应基于本报告继续处理候选任务的抽样复查和剩余疑点。`rl_train_screened.jsonl` 是候选文件；`configs/grpo.toml` 指向 8 条起步文件。

没有改动 `processed/` 原始六个划分、数据库、任务标准操作、评分函数或已公布的 14 条开发集对照结果。最终测试只读取 ID 检查训练集不相交，没有查看测试目标或运行模型评测。审计只用本地 CPU 环境和现有数据，新增费用为 0 元。

## 与原项目的对应关系

本项目固定的是 tau2-bench **v0.2.0 / `f8de30c`**。核对了上游 2026-10-12 的 `main` 提交 `4ce7c03` 的[环境评分器](https://github.com/sierra-research/tau2-bench/blob/4ce7c0397c1eb65c9bbe59aeacfe1ca44a1cd699/src/tau2/evaluator/evaluator_env.py)、[Retail 工具](https://github.com/sierra-research/tau2-bench/blob/4ce7c0397c1eb65c9bbe59aeacfe1ca44a1cd699/src/tau2/domains/retail/tools.py)、[政策](https://github.com/sierra-research/tau2-bench/blob/4ce7c0397c1eb65c9bbe59aeacfe1ca44a1cd699/data/tau2/domains/retail/policy.md)和[更新日志](https://github.com/sierra-research/tau2-bench/blob/4ce7c0397c1eb65c9bbe59aeacfe1ca44a1cd699/CHANGELOG.md)，源码及 SHA256 保存在 `outputs/review/pre_grpo/upstream/`。当前上游已经修订任务并调整接口，因此没有混用新版源码、任务或分数。

tau2 的 Retail 评分主要通过以下步骤完成：重放客服轨迹得到预测数据库；在独立的初始数据库执行标准操作；比较两份数据库最终哈希；依据任务声明的 `reward_basis` 合并数据库、沟通和动作等组件。本项目沿用这些确定性评分器，并额外把参考操作执行失败、基础设施错误与业务失败分开。来源分别是 `third_party/tau2-bench/src/tau2/evaluator/`、`src/retail_agent/reward.py`，当前上游同路径源码见 `outputs/review/pre_grpo/upstream/`。

本次 364 条任务声明了 `DB` 和 `COMMUNICATE`，但 `communicate_info` 全部为空；因此实测核心奖励等于最终数据库是否匹配。`ACTION` 没有列入这些任务的奖励依据。上游的 Retail 政策要求身份验证、逐笔写操作确认、只处理本人的订单、正确解释与必要时转人工，但这些要求**不会被当前数据库奖励完整证明**。不能将业务成功率解释为政策合规率。

## 实际核查

| 核查 | 结果 | 解释 |
| --- | ---: | --- |
| 训练任务参考操作重新重放 | 364/364 成功 | 与旧版全量构建证据独立；只能证明标准操作可执行 |
| 训练任务参考评分 | 364/364 为 1 | 不能证明任务描述和标准操作语义一致 |
| 与初始数据库隔离、重置、错误目标判分 | 364/364 通过 | `reference_probe` 重新执行 |
| 顾客已知商品/规格与数据库不符 | 2 条任务 | 包含 1 条已知商品不存在和 1 条多项规格不符 |
| 任务提及账户未拥有的商品 | 65 条线索 | 同时包含确实矛盾的购买诉求与合法的库存咨询或应拒绝请求，逐条保留线索，不当作 65 条确定错误 |
| 标准地址的字段在任务信息和现有地址均无来源 | 15 条线索 | 可能由对话澄清，但必须复核顾客模拟器是否能提供 |
| 省略全部默认地址写操作仍得满分 | **33 条** | 最终状态奖励无法区分其中的中间过程；已隔离 |
| 理由称需要换尺码而标准操作未换尺码 | 7 条线索 | 有些可能是附带任务或理由摘要不准确，已隔离 |
| 自动疑点并集 | 115 条任务 | 各原因重叠；不是错误条数相加 |

典型证据：

- `retail_103` 的顾客指令要求退书架、拼图和背包；账户实际订单只有水壶、鞋等，标准答案只有地址修改。这是任务叙述与数据库、标准操作的不一致，参考奖励为 1 也无法揭示。
- `retail_122` 明确说账户没有跑鞋，却要求把顾客所说的“跑鞋”解释为哑铃后退货。任务会把正常澄清或拒绝错误商品的客服置于不利奖励位置。
- `retail_124` 要求先改默认地址、后续再恢复；省略两次默认地址操作，其他参考动作照常执行，仍拿到 1 分。33 条同类任务均做了省略实验，结果为 1。
- `retail_500` 的描述包括键盘选项、手机地址和手机容量三项修改，标准答案只有键盘修改。这类漏标目标已作为已知限制记录，候选池后续仍需进一步语义抽检。
- 已公开开发样本 `retail_501` 仍保留原评分和原划分：顾客把耳机称为“牛仔裤”并要求“大尺码”，标准操作却换耳机连接方式。此项只用于开发集疑点说明，未纳入训练文件。

`outputs/review/pre_grpo/train_audit.json` 保存每条任务的执行结果、商品选项变化及原始顾客指令；`review_manifest.json` 保存每个训练 ID 的状态和原因。`semantic_packets.json` 帮助对照场景文本、用户订单与写操作。检查脚本的 SHA256 和原始输入 SHA256 都写入清单。复核命令：

```bash

.venv/bin/python scripts/finalize_rl_review.py
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -p 'test_reward.py' -v
```

## 起步训练集和奖励约定

起步集为 `retail_10`（复合任务）、`retail_131`（默认地址）、`retail_174`（退货）、`retail_301`（换货）、`retail_410`（订单商品）、`retail_444`（取消）、`retail_494`（订单付款）、`retail_540`（订单地址）。这 8 条逐条核对了顾客目标、原始订单、商品规格/库存、支付方式或地址、标准写操作，并重新重放。相应简短理由保存在清单。起步集只用于阶段 05 的接口和一次更新验证，规模太小，不能据此宣称训练后业务能力提升。

阶段 05 的奖励沿用 `evaluate_task` 的任务配置：完整轨迹、独立数据库、`completed` 且最终业务结果匹配得 1；错误目标、无效操作后的错误状态、不完整结束得 0；API、环境、参考执行等基础设施错误抛异常，不作为 0 奖励样本。此次**没有**把标准操作序列当成客服必须逐字复现的答案，也未改写原金标准。

政策相关指标另行记录：身份查询是否在读取用户私有信息和写操作前成功；写操作是否针对该用户；每笔写操作之前是否列出具体内容并得到顾客确认；工具调用协议、是否正确处理不支持的请求及转人工；说明是否与工具事实相符。当前代码只对部分协议做硬性校验；对语言确认和解释的自动检查仍不完整。因此这 8 条可以用于验证 GRPO 的采样、损失掩码与真实参数更新；不能仅用这一奖励宣称“合规客服”训练完成。

正式扩量的条件是：对 `screened_candidate` 继续按业务类别和场景模板抽查；处理高风险语义歧义，尤其是开放式多选变体、漏标目标与人工标记的 115 条；制定可执行且经过反例测试的政策指标。评估时同时报告业务成功与政策专项结果，最终测试仍按封存方案执行。
