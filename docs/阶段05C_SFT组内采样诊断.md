# 阶段 05C：SFT 组内采样诊断

当前（2026-10-13）：已完成 8 个固定目标完整组、32 条真实轨迹与用户确认的有限国家等价奖励修正。29 条可用任务在新奖励下的 145 个场景及两环境合并 126 项回归通过；官方严格成功 13/32，训练奖励认可 14/32，仅纠正一条误判。尚未启动 GRPO 参数更新。当前详细结果见“国家等价修正最终验收”部分；下方保留原始严格评分和历史断点。

## 固定条件与记录

在查看结果前固定 TRAIN 清单：131、174、301、410、444、494、540、213、222、196，均为首批已复核的原始任务。覆盖七类业务，共 8 条单业务、2 条复合业务；单业务也可能涉及多笔订单。组大小 4，温度 0.8，不做 top-k/top-p 裁剪。随机种子为 `42 + 组序号×4 + 组内序号`，序号从 0 开始。同组共享一次真实顾客开场，每次尝试重新创建数据库和顾客实例。

固定使用已评测的 Qwen3-4B SFT 适配器、本机 MLX 4-bit 底座、非思考模式。完整轨迹上限 16,384 token，每客服回合最多 512 token，每任务最多 24 个客服动作。客服使用实际追加 token；顾客与工具反馈保留注意力、损失掩码为 0。不截断、补造结束符、规范化已采样历史或用随机奖励代替判分。

主要文件：

- `configs/grpo_diagnostic.toml`：事先固定的任务和阶段预算。
- `src/retail_agent/grpo_diagnostic.py`：MLX 随机采样、按实际温度记录概率、逐 token 留痕、完整组统计和独立复核；没有优化器。
- `src/retail_agent/grpo_rollout.py`：复用 05B 多轮交互，新增可选进度回调。故障继续传播，不作为客服零分。
- `outputs/review/phase05c/sft_groups_20261012/`：manifest、完整 traces、实时 events、summary、verification、阶段预算与实际执行源码快照。
- `outputs/logs/phase05c_sampling.log`：真实运行日志。

## 查到的问题

1. **MLX tokenizer 兼容错误，已修复。** 首次采样时 `TokenizerWrapper` 不支持 Python 的 `len()`，真实 token 已留痕，但没有可评分轨迹。TokenTape 改为缓存 `get_vocab()` 的大小，仍拒绝越界 ID。新增真实包装对象回归检查，后续 12 条交互验证了该接口。首批失败目录单独保留，没有混入成绩。
2. **退货的订单与商品绑定错误。** 失败轨迹拼错 `get_order_details`，或把两笔订单的商品 ID 混在一起；另有错误退款方式、错误恢复失败。完整成功轨迹正确分开订单并选择原付款方式。两个部分完成轨迹只正确完成第一笔退货。这不是只靠奖励函数增加小数就能消除的错误。
3. **换货与顾客目标漂移。** 固定目标为白色 M 号头盔；部分轨迹中客服误报库存后，顾客接受蓝色 M 号等替代方案，而金标准仍是白色 M 号。其他轨迹还出现选错变体、对已经申请换货的订单重复调用、无效转人工等问题。应区分模型错误与目标漂移，保留现有四次零分，不能看到结果后换金标准或删除失败任务。
4. **顾客服务故障，未修复。** `retail_410` 的第一次尝试收到 `余额读取失败：ConnectionError`。现有有限重试用尽后整批停止；没有追加零分或运行下一任务。下一次付费运行前需要核对连接和只读余额查询。
5. **评分复核的 JSON 表示差异，已修复。** 内存中的子目标为 tuple，JSON 保存后为 list。首次独立复核因 Python 对象类型不同误报；已确认序列化数值一致，改为逐字段比较 JSON 值。反例测试仍拒绝评分、token、概率、掩码或提示记录被篡改。
6. **API 记录关联待补齐。** 当前实时事件读取 `api_record`，实际顾客返回字段为 `api`，导致事件中的关联字段为空。完整费用与用量已写入独立账本，不影响客服动作或业务判分；继续工作时应修正字段并补验关联。现有实时事件不得回填伪装成当时已记录。

### 本次修复及新发现

1. **顾客 API 记录关联。** 新事件读取实际返回的 `api` 字段，并逐条与真实费用账本比较。旧关联为空的事件没有回填。新诊断目录保存执行时源码快照，复核同时检查源码、恢复来源、种子、提示、掩码和 token 概率。
2. **余额连接与记账。** 余额查询短时缓存 60 秒，缓存余额扣除共享账本中的新增费用及未知用量预留。成功生成取得用量后立即记账，不再要求额外余额 GET；失败连接池清理后有限重试。只读健康检查三次通过，后续采样未再因余额 GET 中断。未知计费仍保留预留上界。
3. **固定顾客目标。** 诊断显式启用 `scenario_locked_v1`，不修改旧开发集顾客条件。四项真实 API 挑战检查中，顾客均坚持原白色 M 号目标；真实取消轨迹也证明顾客能接受已送达订单不可改址的政策说明，继续处理合法取消请求。提示规则不是所有场景的形式化保证。
4. **顾客输入保护。** 一条 24 动作对话达到 32,078 字节，触发早期 32KB 保护，未计业务零分。诊断单独改为 64KB，仍保留完整公开历史、预留费用与阶段硬限额；默认旧试跑保持 32KB。真实失败输入已只读复现，新测试覆盖保留历史、超限拒绝与预算拦截。
5. **数据身份矛盾。** retail_494 的 known_info 给出 bob@example.com，实际工具映射为 bob_ellis_1507；目标订单归 bob_harris_382。原参考动作使用正确用户的认证信息，离线参考奖励可为 1，但顾客提供的邮箱会指向别人。此前验收漏查了这个字段。本次核对全部 30 条场景的现成身份信息，隔离 494，另导出保持原始行不变的 29 条 `rl_train_ready.jsonl`。原始六个划分、数据库和历史 30 条池均未改。GRPO 配置与启动预检使用新池；整组采样在 API 调用前拒绝这种身份矛盾。脚本验收仍不等于完整政策与全部文本语义已证明正确。
6. **国家等价写法误判，已确认修正。** retail_540 的 trial 0 正确提交所有地址字段，仅 country 为 United States 而不是 USA，工具成功、身份检查通过，严格奖励仍为 0。独立重放确认：只统一国家写法，整个最终数据库即与参考状态相同。经用户确认，正式评测保留上游严格分数，训练奖励只接受 USA、US、United States 的有限等价关系；不放宽街道、州、邮编、订单、退款或付款检查。原始分数和轨迹保留，另存 v2 新评分，最终验收见文末。
