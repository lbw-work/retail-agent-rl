# Retail 数据集 v2：离线重建与验收

日期：2026-10-11。版本：`retail_full_v2`。

本次全量审查现成 Retail 数据，保留 8,111 个 SFT 目标回合和 514 个 RL 任务。
采用七类售后业务、单一与复合任务、完整历史到 16,384 token、SFT/RL 联合整组划分。
本次新增付费费用为 0 元，没有调用顾客 API、加载客服模型、租 GPU 或开始训练。

## 3. 实际规模与联合划分

| 数据 | train | dev | test | 合计 |
| --- | ---: | ---: | ---: | ---: |
| SFT 目标回合 | 5,682 | 1,215 | 1,214 | 8,111 |
| SFT 来源对话 | 692 | 149 | 151 | 992 |
| RL 任务 | 364 | 75 | 75 | 514 |

SFT 回合比例为 70.05% / 14.98% / 14.97%；RL 为 70.82% / 14.59% / 14.59%。
这是一套完整候选池，实际 SFT 回合数、RL 采样次数及最终评估次数仍需预算试跑决定。
与旧版相比，SFT 训练侧从 1,506 增至 5,682，RL 训练侧从 42 增至 364。

分组使用全部原始行中的用户、邮件、订单、场景，以及规范化的诉求词面模板。
相同模板至少 8 个词时连接；近似模板至少 12 个词、词集合 Jaccard ≥0.75 且字符相似度 ≥0.90 时连接。
历史只读并行查询可以按已有对应返回改排为顺序查询；不生成顾客回合、不改写写操作。
分组在 SFT/RL 之间共同生效，不能为了比例把一个关联组拆开。

当前纳入数据共 596 个联合关联组；旧开发侧的 24 个组、旧最终测试侧的 29 个组作为固定锚点。
三组侧之间的已识别实体、关联组交集均为 0，旧 dev/test 侧无冲突。
四个数据库的全部用户 ID 和订单 ID 均符合本次实体识别格式。
共享商品目录、商品规格与通用付款编号不作为顾客身份分组键。

**SFT test 只封存，不用于训练、调试、选择检查点或补足某类训练样本。**
同一 dev 侧的 SFT/RL 可以关联，因为它们共同用于开发；dev 成绩不能作为独立最终成绩。
未命中词面规则的语义近似模板仍可能存在，当前零交集不证明任意语义层面的绝对无泄漏。

## 4. SFT 质量、长度与训练成本含义

全部 11,395 个 Retail 原始目标回合均有纳入/排除记录。
纳入条件包括来源成功、消息和工具参数结构可用、历史工具调用/返回配对、存在先前身份查询，
以及写操作前顾客语句通过保守的明确确认词面检查。
独立 `reasoning`/`thinking` 字段不进入目标或历史；可见内容中的思考标签需复查。
保留完整上下文，对格式与质量通过的候选使用固定 Qwen tokenizer 渲染和计数。

| 排除原因 | 回合数 |
| --- | ---: |
| 消息与工具混合、或目标包含多个工具，不符合单动作协议 | 2,479 |
| 历史包含并行写操作，不能直接改排 | 519 |
| 写操作之前的顾客语句未通过明确确认词面检查，待复查 | 166 |
| 来源 `correct/reward` 未通过成功条件 | 73 |
| 可见内容含思考标签，待复查 | 47 |
| 合计 | 3,284 |

“待复查”不等于已经证明错误。词面确认可能误排合法的自然语言，也可能漏掉语义问题。
没有为了扩大数量编造确认、修改业务参数或保留原始失败样本。
8,111 个纳入回合中，4,663 个回合的历史包含已按现有返回改排的只读查询批次。

| 完整序列长度 | train | dev | 封存 test | 合计 |
| --- | ---: | ---: | ---: | ---: |
| ≤8,192 | 4,661 | 995 | 998 | 6,654 |
| 8,193～12,288 | 1,014 | 220 | 213 | 1,447 |
| 12,289～16,384 | 7 | 0 | 3 | 10 |

通过上述检查的候选最大长度为 14,209 token；本次没有因超过 16,384 而排除或截断的样本。
每条纳入数据都核对 generation prompt 是完整训练序列的精确 token 前缀，目标 token 数必须为正。
这验证了当前目标回合的边界；训练阶段仍需验证实际 labels/collator 只监督目标客服 token。

| token 数量 | train | dev | 封存 test |
| --- | ---: | ---: | ---: |
| 含完整历史的序列 token 总量 | 37,683,631 | 8,076,585 | 8,065,844 |
| 当前目标回合的监督 token 总量 | 679,469 | 145,168 | 141,247 |

训练侧一轮包含约 3,768 万完整序列 token，虽然监督目标仅约 68 万 token，
历史仍参与模型前向计算。预算估算必须使用完整序列的显存、吞吐和时间，不能只按监督 token 数估算。

七类写操作各抽查一条源示范，核对“客服摘要 → 顾客确认 → 目标参数”，记录在 `sft_spot_review.json`。
这是 7 条定向抽查，不能冒充 8,111 条示范的全量语义审查。
SFT 数据未为每段历史提供可唯一匹配的数据库快照，因此本次没有声称把所有历史工具返回逐一执行重现。

## 5. 七类业务的实际覆盖

| 写操作 | SFT train 目标 | SFT dev 目标 | SFT 封存 test 目标 | RL train 涉及任务 | RL dev | RL test |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 取消待发货订单 | 147 | 31 | 32 | 56 | 14 | 16 |
| 已送达商品退货 | 151 | 32 | 32 | 89 | 18 | 17 |
| 已送达商品换货 | 63 | 12 | 12 | 72 | 17 | 17 |
| 修改待发货订单地址 | 134 | 27 | 29 | 166 | 25 | 25 |
| 修改待发货订单商品规格 | 86 | 17 | 20 | 95 | 20 | 20 |
| 修改待发货订单付款方式 | 97 | 20 | 21 | 44 | 9 | 10 |
| 修改用户默认地址 | 1 | 0 | 0 | 120 | 26 | 25 |

SFT 列统计当前监督目标是该工具的回合，不代表覆盖该工具的完整对话数量。
RL 列统计涉及该业务的任务；一个复合任务可进入多列，不能把各列相加当作任务总数。

**默认地址业务是主要覆盖短板：SFT 只有一条写操作示范，RL 训练中却有 120 个涉及任务。**
不能把重复复制这条示范当作新增独立数据，也不能挪用 dev/test 的示范补训练。
后续先检查原始模型/SFT 模型能否迁移相近的订单地址修改行为，再判断该类任务能否产生有效 RL 优势。

| RL 不同写操作类别数 | train | dev | test |
| --- | ---: | ---: | ---: |
| single：1 类 | 121 | 29 | 28 |
| pair：2 类 | 208 | 38 | 39 |
| complex：≥3 类 | 35 | 8 | 8 |

这里按不同写操作类别划分，一类业务也可能涉及多个订单或多次操作。
纳入任务参考工具链长度：train 为 3～14 次，dev/test 为 3～12 次。
参考链没有真实顾客澄清回合，不能据此断言当前 24 个客服动作上限适合全部复合任务。

## 6. RL 任务逐条执行与隔离

全部 563 个原始 Retail 任务都实际执行过参考工具链：工具执行均无报错，参考数据库奖励均为 1。
随后检查口头宣称、错误目标写操作、独立状态、重置以及评分器不修改运行中的数据库。
最终隔离 49 个任务，保留 514 个。

| 隔离原因 | 任务数 |
| --- | ---: |
| 不执行业务动作，只说“完成”也得 1 分，缺少可区分的数据库信号 | 15 |
| 任务规格或参考动作待语义复查 | 34 |

15 个无区分度任务主要是查询、拒绝或转人工场景。这些场景可以有业务价值，
但当前参考动作不改变数据库，告知要求又为空，无法支持本版采用的数据库结果奖励。
本次隔离，不自行增加文本奖励、改变上游奖励条件或用虚构零分制造有效性。

34 个待复查任务共触发 35 个标记，存在一个任务触发多类标记：

- 30 个包含两种合法取消原因的文本，先保守隔离；部分文本可能已明确具体原因，需要单独语义复查。
- 2 个参考取消原因没有命中对应原因或同义表达。
- `retail_130` 的顾客目标要求退回 PayPal，参考动作退回信用卡。
- 2 个参考换货/修改商品动作包含原规格与新规格相同的项。

旧试跑任务 `retail_107` 属于取消原因多个选项待复查；没有将金标准原因注入顾客或客服提示。
所有纳入的 514 个任务均有参考奖励 1、口头宣称奖励 0、错误目标奖励 0，
以及隔离/重置/评分非修改的当前版本执行证据。
未发现需因旧 dev/test 侧冲突而隔离的关联组。

顾客目标、金标准动作和数据库路径单独存放在任务对象中，客服初始 prompt 只有公开政策。
终局奖励当前真正起作用的是数据库结果，告知条件为空。
**数据库成功不能证明身份核验、订单归属、逐项确认、退款解释等完整对话政策合规。**
规则审查继续作为辅助指标；本次不声称完成每个任务的全部语义检查。

## 7. 地址字段核查

四个快照都有地址，位于 `users[user_id].address` 和 `orders[order_id].address`。
每个地址包含 `address1/address2/city/state/country/zip`。
它们是嵌套对象，不是顶层独立的 `address` 表。

| 快照 | 用户 | 订单 |
| --- | ---: | ---: |
| db_1 | 1,700 | 2,894 |
| db_2 | 1,700 | 4,475 |
| db_3 | 700 | 1,503 |
| db_4 | 1,500 | 3,941 |

修改用户默认地址和修改某个待发货订单地址是不同工具，不能默认其中一个自动同步另一个。
本次逐条参考链使用内存副本，不改动磁盘快照；独立验收再核对原文件校验值。

前两个入口用于新版；最后一个只复查旧阶段三，不发 API 请求。
当前仅保留新版 build_dataset/verify_dataset 入口；旧版专用审计代码已删除。

- `reports/reference_checks.json`：563 条原始任务的实际参考与对照执行记录。
- `reports/data_audit.json`：规模、类别、长度、token、隔离原因和交集。
- `reports/verification.json`：独立来源、全部纳入 SFT token、当前 RL 证据和旧留出节点验收。

不把证据检查描述为又执行了一轮 563 个任务。第二次重建在相同输入下复用 RL 证据。

## 9. 下一阶段的门槛

数据候选池已扩大，SFT/RL 实际训练仍未实现。下一阶段先完成离线目标掩码/collator，
用真实长短样本核对监督范围；再准备预算受控的单次更新和三个长度桶的显存/吞吐实测。
训练配置中的 5,682 是候选池行数，75 是封存 RL 任务数，不是已授权的付费训练/评估量。

正式训练前还需补测新版业务与复合任务的模型交互、终止上限和默认地址冷启动能力。
之后按类别和难度选取预算能覆盖的训练量，记录完整实验和费用。
不能从数据验收直接推导“模型已经能完成七类售后”或“50 元能训练全部候选池”。
