# 原模型与 SFT 开发集评测

评测日期：2026-10-12。数据：retail_full_v2。范围：预先固定的 14 条开发任务，各执行一次，封存 test 未用于生成、训练或选择检查点。

本轮原模型业务成功 **3/14（21.4%）**，SFT **8/14（57.1%）**，增加 5 条、35.7 个百分点。同任务有 6 条从失败变成功，1 条从成功变失败；两组各有 2 条共同成功、5 条共同失败。这个结论仅描述本轮小样本，不代表总体性能或统计显著提升。

## 评测条件

- 底座：Qwen/Qwen3-4B，固定 revision `1cfa9a7208912126459214e8b04321603b3df60c`。
- SFT：5,682 条 train、711 步、1 epoch；r=16、alpha=32，q/k/v/o 四类模块。真实适配器 SHA256 `e941d9338cc9879a90e235615f525544b1e85f6dccd7f0662fe308960f14de49`。
- 本机 MLX 4-bit 底座，两组只差是否加载 SFT LoRA；LoRA 转置加载，不合并、不重新量化。训练使用 NF4，与本机量化方式不同；本轮不是服务端 CUDA 性能测试。
- 客服贪心、非思考，512 token/动作、24 动作/任务、16,384 上下文 token。每条轨迹独立数据库，相同工具、政策和判分器。
- 顾客：`deepseek-flash`，非思考、temperature=0；固定场景，随客服回复生成反馈，不强制两组逐字相同。远程 API 不保证绝对确定性。
- 任务在读取模型结果前选择：seed=42，七类单业务各一条，随机七条复合任务。单业务分类指金标准写操作种类，仍可能含应拒绝的其他请求。
- 两组使用同一精确 token 前缀缓存。两条公开 dev 提示验证缓存开关生成 token 一致；缓存只复用一致前缀，不保留另一任务的私有状态作为输入。

## 改善与剩余问题

**已观察到的改善。** 换货、退货、修改订单商品、默认地址修改由 0 变 1；两个地址复合任务也由 0 变 1。`retail_173` 中，SFT 在修改前读取原地址，之后能按顾客要求恢复；原模型没有保存原值，恢复阶段反复追问。这体现了完整工具流程的改善。

**退步案例 `retail_30`。** SFT 已执行付款更新，但最后把投诉解释文字和 `transfer_to_human_agents` 放在同一回合，违反单动作协议，整个任务计 0。原模型本轮计 1。不能只展示改善案例，也不能把已经完成的部分操作当作完整成功。

**多订单与反馈修复。** `retail_562` 中，SFT 地址调用多次漏掉必需的 `order_id`，收到明确验证错误后仍重复相同参数，最终达到 24 动作上限。`retail_147` 中，将不同订单的商品 ID 放进同一个退货调用，收到 Some item not found 后重复提交，最终转人工，数据库目标没有完成。

**商品查询与无依据陈述。** `retail_417` 中，SFT 反复使用不存在的 `1008292230`，没有完成商品修改；`retail_147` 读取订单后未调用 `get_product_details` 就声称没有可换库存。政策文字和工具 schema 已提供，但模型仍未稳定地用正确工具验证自己的判断。

**身份流程的专项检查。** 这里只检查“首次写工具调用前，是否已有成功的 email/name+zip 身份定位工具”，不是完整合规评分。原模型 10 条有写尝试的轨迹中有 2 条缺少该步骤（`retail_422`、`retail_364`），且两条数据库奖励都是 1；SFT 14 条有写尝试的轨迹中有 1 条缺少（`retail_119`，最终奖励 0）。SFT 仍在该任务中身份查询失败后读取、修改订单。首次身份定位改善不等于逐次确认、订单归属、退款说明等全部合规。

**成功轨迹也可能有政策问题。** `retail_422` 两组数据库奖励都是 1，但 SFT 没有清楚说明 T-Shirt 不能改成不同产品类型 Sneakers，而是反复以库存信息不足为理由，并表示可替换。主奖励没有覆盖这种对话质量问题。

## 数据质量疑点

`retail_501` 顾客把无线耳机称为“牛仔裤”并要求大号；商品选项没有对应尺寸变化，而参考操作将无线耳机换成有线耳机。金标准可以成功执行，不足以证明它与顾客目标语义一致。该任务标为待复核，两组都计 0，仍保留在预先固定的 14 条主成绩里，不在看到结果后删除任务提高成绩。

其他任务未做全量自然语言与金标准语义审计。本轮业务成功率应与这些数据及奖励覆盖限制一起解读。

## 证据与费用

保存位置：`outputs/evaluation/dev_original_sft_20261012/`。`manifest.json` 记录任务、模型/适配器哈希、工具 schema、运行代码哈希、依赖、顾客和推理配置；`traces.jsonl` 记录完整真实轨迹；`summary.json` 为原始汇总；`analysis.json` 为分类和专项检查；`verification.json` 为复核结果。

独立从磁盘读取 28 条轨迹，检查任务完整性、无重复、同任务两组齐全，重新汇总并逐条重放官方奖励；28 条均与运行记录一致。复核没有调用顾客 API。

首轮在第二条任务发生余额接口 ConnectionError，记录独立保留在 `outputs/evaluation/dev_original_sft_20261012_interrupted/`，未混入主成绩。只读余额查询增加最多两次重试后，按同一清单重新执行；未修改任务或答案。

主批次顾客 API 记账上界 **0.241880 元**，加上首次中断 **0.010177 元**，本轮合计上界 **0.252057 元**。这不是 GPU 费用或完整项目总账；实际扣费以平台账单为准。用户确认 GPU 费用不超过 35 元，本轮 API 硬限额仍在 1 元以内。

审计/推理环境回归：45 项通过、8 项训练专项跳过；独立训练环境 SFT 专项 8/8 通过。权重转换与完整性、只读查询有限重试均有回归检查；未重新执行服务器上的 GPU 训练。

## 下一阶段的依据

先复核自然语言目标、候选商品选项和参考操作的一致性，再在 TRAIN 侧同类任务上验证 RL 最小更新。重点是必需参数补全、按订单拆分写操作、利用工具错误修正、查询商品后再回答、一直遵守单动作协议并完成任务。不要把本轮 dev 轨迹回流为训练样本，也不要因这些结果改封存 test。

后续扩大到全部 75 条 dev、重复试验，再按冻结方案执行最终 original / SFT / SFT+GRPO 对照。当前不能宣称 RL 已训练、最终测试已通过或全面政策合规。
